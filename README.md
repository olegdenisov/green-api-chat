# GREEN-API Telegram-чат

[![CI](https://github.com/olegdenisov/green-api-chat/actions/workflows/ci.yml/badge.svg)](https://github.com/olegdenisov/green-api-chat/actions/workflows/ci.yml)

Веб-чат для отправки и получения текстовых сообщений Telegram через
[GREEN-API](https://green-api.com/). Backend нет — запросы идут из браузера. Внешний вид — по
мотивам [web.max.ru](https://web.max.ru/).

Деплой: **https://green-api-chat-three.vercel.app/** — Vercel, автоматически с ветки `main`
(см. «Деплой и CI»).

CI на GitHub и деплой Vercel работают, CSP на деплое отдаётся и не мешает странице; запросы к
GREEN-API с домена деплоя (в т.ч. CORS опроса) ещё не проверены — см. «Известные ограничения».
Форма логина проверяет инстанс (`getStateInstance`), при необходимости включает настройки
уведомлений (в т.ч. `outgoingWebhook` для статусов доставки) и сохраняет креды в
`localStorage`. На экране чата: кнопка «+» раскрывает форму нового чата по номеру телефона
(`checkAccount`; уже известный номер открывается без запроса), отправка текста со статусами
«отправляется» / «отправлено» / «доставлено» / «прочитано» / «не отправлено · Повторить»
(доставлено/прочитано — из уведомления `outgoingMessageStatus`), удаление чатов с историей.
Чаты и сообщения хранятся в `localStorage` и синхронизируются между вкладками; «Выйти» стирает
креды и все данные. На узком экране — либо список, либо окно чата. Пока пользователь залогинен,
приложение опрашивает очередь уведомлений GREEN-API: ответы из Telegram и сообщения,
отправленные с телефона, появляются в чатах; новый собеседник — новый чат (не выбирается).
Опрашивает одна вкладка (Web Locks), остальные получают данные через `localStorage`. При
сбоях сети — полоса «Соединение…», при недействительных кредах — выход с тостом.

Вёрстка: тема Mantine на палитре №4705 (color.romanuke.com: индиго, лаванда, персик, пудровый
розовый) вместо прежнего синего акцента «по мотивам web.max.ru», своя тёмная шкала с оттенком
индиго; аватары — один из пяти цветов палитры по хешу `chatId` (токены `--ga-avatar-N-*`),
список чатов с превью, временем и активной строкой (тинт + полоса слева), разделители по дням,
свои иконки (инлайн-SVG, в т.ч. статусы доставки); светлая и тёмная схемы — по системной
(`prefers-color-scheme`), переключателя нет. Логотип — свой, не товарный знак MAX.

Дизайн, API, модель данных и этапы:
[docs/plans/20260923-telegram-chat-design.md](docs/plans/20260923-telegram-chat-design.md).

## Как пользоваться

1. Заведите инстанс Telegram в [консоли GREEN-API](https://console.green-api.com/) и
   авторизуйте его. Из консоли нужны `idInstance` и `apiTokenInstance` (при необходимости —
   `apiUrl`, если он отличается от подставляемого по `idInstance`).
2. Введите их в форме логина. При необходимости приложение включит уведомления инстанса
   (`setSettings`) и очистит `webhookUrl`: **инстанс перезапускается, применение занимает до
   5 минут** — входящие сообщения появятся в течение ~5 минут после первого входа.
3. Нажмите «+» в шапке списка, введите номер телефона получателя (международный формат,
   10–15 цифр; пробелы и `+` допустимы) и создайте чат — форма закроется, фокус перейдёт в
   поле сообщения. Escape или повторный «+» закрывают форму без создания. Напишите сообщение.
4. Ответ из Telegram появится в чате.

## Локальный запуск

Нужны Node.js >= 22 и pnpm 12. Версия pnpm зафиксирована в `packageManager` (`package.json`),
проще всего поставить её через Corepack, который входит в Node.js.

1. Склонируйте репозиторий:

   ```sh
   git clone https://github.com/olegdenisov/green-api-chat.git
   cd green-api-chat
   ```

2. Включите Corepack (один раз на машину), он подставит нужную версию pnpm:

   ```sh
   corepack enable
   ```

3. Установите зависимости и запустите dev-сервер:

   ```sh
   make install   # или pnpm install
   make dev       # или pnpm dev
   ```

4. Откройте адрес, который выведет Vite (по умолчанию http://localhost:5173/), и войдите
   с кредами инстанса — см. «Как пользоваться». `.env` не нужен: `idInstance`,
   `apiTokenInstance` и при необходимости `apiUrl` вводятся в форме логина.

Продакшен-сборка локально:

```sh
make build     # проверка типов и сборка в dist/
make preview   # раздать dist/ (по умолчанию http://localhost:4173/)
```

Остальные команды:

```sh
make test      # тесты
make check     # lint → format-check → lint-fsd → typecheck → test
make help      # все команды
```

## Деплой и CI

- **CI** — GitHub Actions (`.github/workflows/ci.yml`): на push в `main` и на pull request
  выполняются `pnpm install --frozen-lockfile`, `make check` и `make build` на Node 22 и 24.
- **Деплой** — Git-интеграция Vercel, автоматический: push в `main` — production, PR и
  другие ветки — preview (ссылка — в статусе коммита/PR на GitHub); в репозитории
  только `vercel.json`: пресет `vite`, `corepack enable` перед `pnpm` (Vercel по lockfile
  ставит pnpm 9/10, а проект зафиксирован на pnpm 12) и заголовки безопасности. Деплой Vercel
  не ждёт CI: он идёт независимо от статуса проверки.
- **CSP** (в `vercel.json`): `script-src 'self'` — в `index.html` нет inline-скриптов;
  `connect-src https:` — `apiUrl` задаёт пользователь; `style-src 'unsafe-inline'` нужен
  Mantine. Креды лежат в `localStorage`, токен идёт в URL запросов — поэтому CSP важна.

Статус: CI на GitHub и деплой на Vercel работают. CSP на домене деплоя отдаётся, страница
загружается без нарушений CSP в консоли; запросы к GREEN-API с домена деплоя **не проверены**.

## Структура

[Feature-Sliced Design](https://feature-sliced.design/): слои в `src/` — `app` → `pages`
→ `widgets` → `features` → `entities` → `shared`, импорт только сверху вниз. `widgets` пока
нет — код с одним потребителем живёт в странице.

- `app` — провайдеры и тема, стили, выбор экрана, очистка данных при логауте.
- `pages`
  - `pages/login` — страница логина.
  - `pages/chat` — сайдбар, окно чата, `chat-avatar` и их модели.
- `features`
  - `features/auth` — форма логина, «Выйти».
  - `features/delete-chats` — удаление чатов с историей.
  - `features/receive-messages` — опрос очереди уведомлений, индикатор соединения.
- `entities`
  - `entities/session` — креды, `logout`, клиент API.
  - `entities/chat`
  - `entities/message`
- `shared`
  - `shared/api` — клиент GREEN-API.
  - `shared/config` — срок хранения данных.
  - `shared/ui` — заголовок приложения, `icons` (инлайн-SVG).

Вне `src/`:

- `test/` — тестовые утилиты: мок `fetch` для GREEN-API, заглушка Web Locks.
- `vitest.setup.ts` — настройка тестов.
- `.github/workflows/ci.yml` — CI.
- `vercel.json` — деплой и заголовки.

## Безопасность

Backend нет, поэтому `apiTokenInstance` хранится в `localStorage`. Куки, память и
шифрование WebCrypto от XSS без backend не защищают, а синхронизацию вкладок ломают.
Защищаемся тем, чтобы XSS не появился, и закрываем утечки: строгий CSP без inline-скриптов,
текст сообщений только через React, только HTTPS, `Referrer-Policy: no-referrer`, ошибки без
URL и токена, логаут стирает креды и историю во всех вкладках. Остаточные риски — XSS и
расширения, общий компьютер до логаута. Модель угроз, сравнение вариантов и путь к настоящей
защите (backend-прокси с `HttpOnly`-кукой) — в разделе «Безопасность» дизайн-документа.

## Известные ограничения

- Креды хранятся в браузере (`localStorage`), токен передаётся в URL запросов, как требует
  GREEN-API. Почему так — «Безопасность».
- Одновременные записи двух вкладок в одном тике теряют одну из них (атом пишется целиком).
  Запись лидера может затереть одновременную отправку в другой вкладке, и наоборот; слияния
  по `storage` нет.
- История до первого логина недоступна (кроме событий за последние 24 ч в очереди — они
  появляются при первом входе и воссоздают удалённый чат).
- Только текстовые сообщения и личные чаты.
- Индикатор «Соединение…» — только у вкладки-лидера. Постоянная `http`-ошибка опроса
  (например, `400`, если `webhookUrl` выставили извне после логина) выглядит как вечное
  «Соединение…».
- Свои API-отправки сопоставляются с событиями по точному тексту: если сервер нормализует
  текст — дубль. Сопоставление с `failed` не ограничено по времени.
- После `401` ведомая вкладка может успеть сделать ещё один запрос со старыми кредами —
  второй тост «Сессия недействительна».
- `469` в опросе ждёт максимум 30 с, а не часы.
- Счётчиков непрочитанного, поиска и переключателя темы нет.
- Статусы доставки (`outgoingMessageStatus`) начинают приходить только после перелогина: флаг
  `outgoingWebhook` включается в `setSettings` при входе, у уже сохранённой сессии не
  проверяется.
- `failed`/`noAccount` не показываются статусом в пузыре — в документации GREEN-API у них нет
  `idMessage`, сообщение не сопоставить (ошибка отправки по-прежнему видна из ответа
  `sendMessage`/таймаута).
- Статус, пришедший в очереди раньше, чем сообщению присвоен `idMessage` (ответ `sendMessage`
  или `outgoingAPIMessageReceived`), теряется — сообщение остаётся с «✓».
- Не проверено вручную: CORS запросов `receiveNotification`/`deleteNotification` с домена
  деплоя (`getStateInstance`, `getSettings`/`setSettings`, `checkAccount`, `sendMessage`
  проверены на реальном инстансе локально), сценарий задания на реальном инстансе после
  этапа 6 (в т.ч. на деплое).

Полный список и подробности — в дизайн-документе.
