# Этап 2: клиент GREEN-API (`shared/api`)

## Overview

- Второй из 6 этапов (см. `docs/plans/20260923-telegram-chat-design.md`, «Этапы»).
- Типизированный клиент GREEN-API для Telegram, на котором строятся этапы 3–5: логин
  (`getStateInstance`, `getSettings`/`setSettings`), новый чат (`checkAccount`), отправка
  (`sendMessage`), получение (`receiveNotification`/`deleteNotification`).
- Единая модель ошибок `ApiError` и поддержка `AbortSignal` (нужна polling-циклу этапа 5).
- `shared/lib` на этом этапе не создаём: persist — встроенный `withLocalStorage` из
  `@reatom/core` (решение зафиксировано в дизайне), других утилит пока не нужно.
- Итог: `@/shared/api` экспортирует `createGreenApi`, `resolveApiUrl`, `ApiError`, типы;
  всё покрыто unit-тестами, примеры из документации проверены против типов через
  `satisfies`; `make check` зелёный.

## Development Approach

- **testing approach**: Regular (код, затем тесты в той же задаче)
- каждую задачу завершать полностью до перехода к следующей; коммит на каждую задачу
- **CRITICAL: каждая задача с кодом включает новые/обновлённые тесты**
- **CRITICAL: каждая задача заканчивается зелёным `make check`**
- **CRITICAL: обновлять этот план при изменении скоупа**
- **CRITICAL: форматы запросов/ответов сверять по https://green-api.com/telegram/docs/
  (страницы методов), а не по памяти и не по WhatsApp-версии документации.** Расхождения
  с дизайном — ⚠️ в плане и правка дизайна.
- YAGNI: не делать атомы, UI, разбор уведомлений по чатам, нормализацию номера,
  retry/backoff — это этапы 3–5.

## Testing Strategy

- **unit tests**: `fetch` мокается через `vi.stubGlobal("fetch", vi.fn<typeof fetch>())`;
  глобалы снимаются автоматически — `test.unstubGlobals: true` в `vite.config.ts`
  (добавить в Task 2). Проверяются URL, HTTP-метод, заголовки, тело, разбор ответа и все
  ветки ошибок.
- **мок с отменой**: для abort-тестов мок уважает `signal`:
  `mockImplementation((_, init) => new Promise((_, reject) =>
  init?.signal?.addEventListener("abort", () => reject(init.signal!.reason))))`.
- **fixtures**: примеры ответов и уведомлений из документации — `.ts`-файлы в
  `test/fixtures/green-api/` с `export const x = { ... } satisfies <Тип>`: `tsc -b`
  сверяет примеры документации с нашими типами. Данные — как в документации (вымышленные),
  реальных кредов и номеров нет. `resolveJsonModule` не нужен.
- **e2e**: нет.
- Ручная проверка CORS с реальным инстансом — в Post-Completion.

- Фабрика `createGreenApi(creds)` возвращает объект с 7 методами. Экземпляр без
  изменяемого состояния — при смене кредов создаётся новый (этап 3 будет держать его в
  computed от атома кредов).
- `request()` — единственное место с `fetch`: собирает URL, сериализует тело, разбирает
  ответ, маппит ошибки. Методы — тонкие обёртки с типами.
- Рантайм-валидации ответов нет (без zod): проверка статуса и приведение типа.

## Technical Details

### Credentials и URL

```ts
type Credentials = { idInstance: string; apiTokenInstance: string; apiUrl: string }
// URL: `${apiUrl}/waInstance${idInstance}/${method}/${apiTokenInstance}` [+ `/${receiptId}`]
resolveApiUrl("4100000000") // "https://4100.api.green-api.com"
```

- `resolveApiUrl` делает `trim()` входа, берёт первые 4 цифры; если после `trim` строка
  короче 4 символов или содержит нецифры — `undefined` (форма логина на этапе 3 попросит
  ввести `apiUrl` вручную).
- `request()` кредов не трогает, кроме удаления завершающего `/` у `apiUrl`. Trim полей
  формы — этап 3.
- Токен не логируется и не попадает в `message` ошибок.

### ApiError

```ts
class ApiError extends Error {
  readonly kind: "auth" | "network" | "rate-limit" | "http"
  readonly status?: number
  // поля объявлены явно (erasableSyntaxOnly), конструктор: super(message, { cause }),
  // name = "ApiError"; message — фиксированная строка по kind/status, без URL и токена
}
```

| ситуация | результат |
| --- | --- |
| `signal` отменён — до вызова, во время `fetch` или при чтении тела | причина отмены (`signal.reason`, обычно `AbortError`) без изменений. Правило: `signal?.throwIfAborted()` перед `fetch`, сразу после него и в каждом `catch`; `instanceof DOMException` не проверять (правка ревью: раньше в `catch` было `throw error` — при гонке сети и отмены пробрасывался сетевой `TypeError`) |
| `fetch` отклонён по другой причине (сеть, CORS) | `ApiError { kind: "network" }`, исходная ошибка — в `cause` |
| `401`, `403` | `ApiError { kind: "auth", status }` |
| `469` | `ApiError { kind: "rate-limit", status }` |
| прочие не-2xx (в т.ч. `466` — лимит тарифа) | `ApiError { kind: "http", status }`; непрочитанное тело отменяется (`body.cancel()`) |
| `2xx`, пустое тело **или** тело `null` | `null`. Это поведение `request()`; методы фабрики, кроме `receiveNotification`, бросают `ApiError { kind: "http" }` без `status` (решение Task 4) |
| сбой чтения тела `2xx` (не отмена) | `ApiError { kind: "network", status }`, исходная ошибка — в `cause` |
| `2xx`, невалидный JSON | `ApiError { kind: "http", status }` |

`rate_limit_exceeded` в ответе `200` проверяется не в `request()`, а в обёртке
`checkAccount` (Task 4). Форма описана в документации: `{ status: false, data: { reason:
"rate_limit_exceeded", retryAfter } }` → `ApiError { kind: "rate-limit" }` без `status`,
исходный ответ (с `retryAfter`) — в `cause`.

### Методы

Все методы принимают последним аргументом `options?: { signal?: AbortSignal }`.

| метод | HTTP | запрос | ответ |
| --- | --- | --- | --- |
| `getStateInstance(options?)` | GET | — | `{ stateInstance: StateInstance }` |
| `getSettings(options?)` | GET | — | `Settings` (нужные поля) |
| `setSettings(patch, options?)` | POST | `SettingsPatch` (`Partial<Settings>` без `wid`/`typeInstance`) | `{ saveSettings: boolean }` |
| `checkAccount(phoneNumber: number, options?)` | POST | `{ phoneNumber }` | `CheckAccountResponse` |
| `sendMessage({ chatId, message }, options?)` | POST | как есть | `{ idMessage: string }` |
| `receiveNotification(options?: { receiveTimeout?, signal? })` | GET | `?receiveTimeout=` только если задан | `ReceivedNotification \| null` |
| `deleteNotification(receiptId, options?)` | DELETE | `/{receiptId}` в пути | `{ result: boolean; reason?: string }` |

- `checkAccount` — тонкая обёртка: номер числом; нормализация и проверка пустого номера —
  в `features/create-chat` (этап 4).
- `receiveTimeout` без значения по умолчанию на стороне клиента (сервер: 5 с); этап 5
  передаёт 20.
- `POST` — `Content-Type: application/json`.

### Уведомления (типы, без логики разбора)

```ts
type Notification = IncomingMessageNotification | OutgoingMessageNotification
// Incoming: typeWebhook "incomingMessageReceived"
// Outgoing: typeWebhook "outgoingMessageReceived" | "outgoingAPIMessageReceived"
// messageData — дискриминированный union по typeMessage:
//   { typeMessage: "textMessage"; textMessageData: { textMessage: string } }
//   | { typeMessage: "extendedTextMessage"; extendedTextMessageData: { text: string; ... } }
// текст — extendedTextMessageData.text (сверено на этапе 2)
type ReceivedNotification = { receiptId: number; body: Notification }
```

- В union нет «ловушки» `{ typeWebhook: string }` / `typeMessage: string` — иначе сужение
  по `switch` на этапе 5 не работает. Прочие `typeWebhook`/`typeMessage` приходят в
  рантайме и обрабатываются веткой `default` на этапе 5 — это задокументировать
  комментарием у типа.
- Поля — по примерам документации (`timestamp`, `idMessage`, `senderData.chatId/
  chatType/chatName/senderName`).
